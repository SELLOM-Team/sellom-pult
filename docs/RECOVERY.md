> сценарий C обновлён 29.10.2026 после реального сбоя — плейбук подъёма инструментов без
> перезапуска сессии).

> или после сбоя. Протоколы также продублированы в `MEMORY.md` (Директивы 2 и 3);
> при расхождениях приоритет — у GitHub-репозитория (remote `main`).

## 1. Сценарий A — сброс сессии, окружение живо (`.git` на месте)

1. Прочитать `MEMORY.md` → `worklog.md` (последний Task ID и незавершённое).
2. `git -C /home/z/my-project fetch origin && git status -sb && git log --oneline -5`.
3. Если локальная ветка отстаёт от `origin/main`: `git pull --rebase origin main`.
4. Продолжить ровно с места, отражённого в MEMORY «Текущее состояние» и worklog.
   Завершённое НЕ переделывать.

## 2. Сценарий B — окружение умерло полностью (новая машина/песочница)

1. Запросить у владельца действующий PAT к `sellom-team/sellom-pult`.
2. `git clone https://<PAT>@github.com/sellom-team/sellom-pult.git /home/z/my-project`
3. Прочитать `MEMORY.md` → `worklog.md` → этот файл (`docs/RECOVERY.md`).
4. Проверить BMAD: `cd /home/z/my-project && npm install` (package.json содержит
   `bmad-method@6.12.4`), затем `npx bmad status`. Каталог `_bmad/` закоммичен — должен
   присутствовать после клона; если отсутствует, восстановить:
   `npx bmad-method install --directory /home/z/my-project --modules bmm --tools claude-code,codex --yes --communication-language Russian --document-output-language Russian`
   (скиллы `.claude/skills/` и `.agents/skills/` восстановит установщик).
5. Убедиться, что remote `origin` в `.git/config` содержит токен (после клона — уже есть).
6. Восстановить rust-окружение песочницы, если стёрто (4-й случай 29.10.2026; проверка:
   `ls ~/.cargo/bin` — пусто значит стёрто):
   `curl -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal --default-toolchain 1.99.1 -c clippy,rustfmt`
   затем `source ~/.cargo/env && cargo --version` (ожидается 1.99.1; в `pult/rust-toolchain` пин;
   верификация сборкой `cargo build --workspace --locked` из `pult/`). Проверить SPA:
   `node -v` (24.x); при отсутствии `node_modules` — `npm ci` в `pult/shells/bitrix24`.
7. Продолжить с места «Текущее состояние» из MEMORY.md.

## 3. Сценарий C — инструменты (bash и др.) отвечают ошибками/таймаутами

> Обновлено 29.10.2026 после реального сбоя в бою: канал связи с пользователем (IM-сообщения)
> НЕ зависит от инструментального канала (bash/LS) — он может жить при упавших инструментах.
> У владельца НЕТ кнопки перезапуска сессии — прежнее предписание «перезапустить сессию» НЕПРИМЕНИМО.

Порядок действий (от дешёвого к дорогому):

1. НЕ повторять падающую операцию более 2 раз подряд — после 2 сбоев переходить к шагам ниже.
2. Лёгкая проба живости: одиночная `echo alive`. Отвечает — инструменты живы, продолжать работу.
3. Запасной путь — СУБАГЕНТ: делегировать через Task-инструмент микрозадачу
   (subagent_type: general-purpose) «выполни `echo alive` и верни вывод дословно».
   Субагент исполняется в свежем контексте — его инструментальный канал может
   работать при падении основного (механизм делегирования проверен 29.10.2026, PROBE-1;
   при падении основного канала — первый кандидат на пробу). Если субагент справился —
   узкие задачи (проверка CI через API, чтение файлов, git-операции) можно доверять
   субагентам поштучно, пока основной канал не ожил. Субагенту передавать САМОДОСТАТОЧНЫЙ
   промпт — он НЕ видит контекст сессии (включая токен: подставить в команду в промпте).
4. Если и субагент падает: сообщить пользователю (штатно — канал связи обычно жив) и
   попросить прислать любое сообщение НОВЫМ заходом. Проверено 29.10.2026 в реальном
   сбое: после следующего сообщения пользователя инструменты поднялись САМИ — gateway
   пересоздаёт коннект на новом ходе. НЕ просить «перезапустить сессию» — возможности нет.
5. Прогресс защищён: всё значимое уже запушено (правило «push после каждой вехи»);
   незапушенный хвост восстанавливается по записям `worklog.md`.
6. После восстановления: сверить состояние ПЕРЕД продолжением — шаги 1–4 сценария A
   (`git log --oneline -1`, `git status --short`, worklog, MEMORY «Текущее состояние»),
   затем продолжать ровно с места остановки. Завершённое НЕ переделывать.

## 4. Правила, защищающие прогресс (обязательны всегда)

- После каждой вехи: `git add -A && git commit -m "<веха>" && git push origin main` —
  пуш СРАЗУ после коммита, не откладывая до конца сессии.
- `worklog.md` дополняется ПОСЛЕ каждого значимого шага (не в конце сессии).
- Конфликт «незапушенный локал vs remote»: приоритет у remote (более свежий пуш).
- Коммит-месседжи — английские conventional (`feat/docs/chore/...`), содержимое — русское.
- Языки проекта: общение агентов и документы — Russian (override-слои `_bmad/custom/*.toml`,
  переживают переустановку BMAD).

## 6. Сценарий D — CI-прогоны падают МГНОВЕННО, все джобы, без единого шага

> Задокументировано по реальному сбою 29.10.2026 (два прогона × 2 attempts).

Симптомы (все сразу — этого достаточно для диагноза):
- API `actions/runs/{id}/jobs`: у каждой джобы `steps: []`, `runner_id: 0`,
  `runner_name: ""`, started→completed за 2–4 секунды, conclusion `failure`;
- логи джобы не существуют (`BlobNotFound`);
- ПАДАЮТ ВСЕ джобы параллельных workflow-джобов, включая те, что час назад были
  зелёными на том же коммит-дереве (диагностический приём: `rerun` СТАРОГО
  успешного прогона — упал так же → причина не в новом коде);
- githubstatus.com: Actions `operational` (не инцидент GitHub).

Вывод: аккаунт-уровень — GitHub не выделяет раннер. Наиболее частая причина
для ЧАСТНОГО репозитория: исчерпаны бесплатные Actions-минуты (2000/мес) либо
заблокирован spending limit. Пуш/клон работают (Contents-квота отдельно) —
только CI-раннеры отклоняются.

Действия агента:
1. НЕ копаться в логах джобов (их нет) и не «чинить» код/воркфлоу.
2. Диагностировать по API (Bearer PAT из `.git/config`): jobs прогона →
   `runner_id: 0` + пустые steps; перепустить старый зелёный прогон — упал?
   причина аккаунт-уровня.
3. СООБЩИТЬ ВЛАДЕЛЬЦУ: GitHub → Settings → Billing (учётки) → проверить
   Actions minutes/Spending limits: докупить минуты / поднять лимит / ждать
   сброса месячной квоты. Проверка биллинга API невозможна с Contents-PAT.
4. Локальная верификация коммита при заблокированном CI: полный локальный
   прогон как в CI (fmt --check, clippy --workspace --all-targets --locked
   ГРОМКО rg-гейтом, test --workspace --locked, node-гейты) — фиксируется
   в worklog: «CI заблокирован квотой, верификация локальная».
5. Пушить работу можно (не расходует минуты — раннер не выделяется),
   но каждый пуш создаёт красный прогон: после починки биллинга перепустить
   последний прогон (rerun), а не перепушивать.
6. РЕЗОЛЮЦИЯ 31.10.2026: владелец перенёс репо в публичную организацию
   `sellom-team/sellom-pult` — стандартные раннеры публичных репо Actions-минут
   НЕ расходуют: run #33 (attempt 2) зелёный сразу после rerun. Сценарий D
   закрыт; для будущих сбоев помнить: перенос/публичность — способ разблокировки
   без биллинг-действий.
