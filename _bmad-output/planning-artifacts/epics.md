# Пульт селлера — Epic Breakdown (MVP Ф0)

## Overview

Этот документ — полная декомпозиция MVP Ф0 «Пульта селлера» (канал Битрикс24, WB полная глубина + Ozon чтение обеих схем — решение вопроса 8.1) в эпики и сторис. Вход: PRD Ф0 (35 FR, статус final), addendum (контракты A-1…A-11), Architecture Spine (30 AD, статус final, включая пересмотр стека AD-20 Rust и мандат AD-28 Valkey). Сторис готовы для передачи разработчику (Amelia) через sprint-planning: каждая — размером на одного dev-агента, с проверяемыми критериями приёмки (Given/When/Then) и явными ссылками на FR-N и AD-N. Правила: сущности БД создаются сторис только под собственные нужды (никаких «всех таблиц вперёд»); сторис не зависит вперёд — только от предыдущих; эпики организованы вокруг пользовательской ценности, технические слои — внутри сторис.

## Requirements Inventory

### Functional Requirements

- FR-1: Фильтр периметра «ваш бизнес» (шаг 0 онбординга): не-селлеры получают честный отказ «продукт не подходит», рекомендацию партнёра (рев-шер ≥ 30%) и не попадают в воронку; доля прошедших шаг 0 замеряется (знаменатель активации UJ-1).
- FR-2: Мастер подключения площадок (шаги 1–3): WB — полная глубина FBO/FBS/realFBS; Ozon — чтение обеих схем FBO+FBS/rFBS (вопрос 8.1 закрыт 28.10.2026); токен принимается только после автотеста прав (успех — список прав, отказ — человекочитаемая диагностика); шифрование AES-256; права перепроверяются при каждом синке; обе площадки одновременно в одном портале.
- FR-3: Первичный синк истории: активная часть онбординга ≤ 15 минут, полный первичный синк ≤ 24 часов (гейт: у 80% пилотов канбан жив ≤ 24 ч); прогресс синка виден (%); тяжёлые каталоги 10К+ SKU не блокируют лёгких (инкрементальность A-2).
- FR-4: Маппинг номенклатуры при онбординге (шаг 4): вероятностный матчинг с обучением на подтверждениях; блокинг-предфильтр (категория, бренд, нормализованный артикул); непокрытые SKU — очередь разборов; bulk-маппинг; доля автопокрытия видна; разбор 10К+ SKU — 15–25 чел.-часов.
- FR-5: Пороги алертов и роли команды (шаги 5–6): задаются до первого канбана; приглашения уходят внутри Б24; онбординг завершается канбаном с назначенной ролью и порогами.
- FR-6: Демо-кабинет №1: синтетические реалистичные данные (3 SKU, 2 площадки, инциденты, неделя истории, сезонность, тарифы 2026), весь путь ценности без передачи токенов; данные помечены демо и не смешиваются с реальными порталами.
- FR-7: Виджет Б24 без открытия приложения: остатки и статус дня; обновление с витрин конвейера (лаг ≤ аналитического цикла); клик открывает приложение на соответствующем разделе.
- FR-8: Сбор данных с адаптивным расписанием: версионированные адаптеры WB и Ozon, rate-limit-менеджер, очередь с приоритетами, вебхуки Ozon; новый заказ в канбане ≤ 15 минут; изменение контракта API не роняет поля молча (версии + контрактные тесты + канарейки); rate limit площадки не нарушается ни одним порталом.
- FR-9: Ежечасная сверка контрольных сумм заказов и остатков (площадка vs Пульт) по каждому порталу: расхождение → инцидент с приоритетом и владельцем ≤ 1 часа; 100% расхождений журналируются; авто-восстановление повторным сбором сегмента; не восстановлено за 4 часа → SLA-кейс (FR-11).
- FR-10: Журнал целостности (когда сверялись, что нашли, что исправили) доступен селлеру в приложении вечно; агрегированный статус интеграции по каждой площадке — на автоматической внешней статус-странице.
- FR-11: SLA-компенсация «месяц подписки»: подтверждённая потеря заказа по вине синка (не восстановлена за 4 часа с момента обнаружения) возвращает месяц подписки; безлимитна по числу событий; в канале Б24 — «месяц без начисления усилий» пулу; списание производит биллинг-контур, не поддержка; каждый кейс — в контекстные тесты следующего релиза адаптера.
- FR-12: Обратная запись статусов отгрузок WB FBS/realFBS через action-bus: идемпотентно (повтор не создаёт дубль), с журналом обратных вызовов и повторами при сбоях; все операции записи журналируются; Ozon в Ф0 записи не принимает.
- FR-13: Индекс здоровья 0–100: агрегат зон; в Ф0 активны 4 зоны (заказы, остатки, маржа, инциденты); зоны «цены»/«отзывы» зарезервированы; вырожденные зоны не искажают индекс; состав формулы документирован, пересчёт с каждым циклом витрин.
- FR-14: Очередь «что сделать сегодня» на панели: приоритизированный список из инцидентов, SLA-задач и событий правил; каждый пункт кликабелен (ведёт к сущности); пустая очередь — осмысленный экран «всё под контролем» с цифрами дня.
- FR-15: Ключевые цифры (вчера/неделя/месяц: заказы, выручка, маржа при заполненной финмодели) и мини-карта статуса площадок (синк жив/лаг/инцидент); штамп «данные на момент»; лаг синка виден рядом с цифрами.
- FR-16: Единый канбан заказов: все заказы подключённых площадок и схем (WB FBO/FBS/realFBS; Ozon FBO/FBS/rFBS) на одной доске, колонки «новый → к сборке → к отгрузке → в пути → доставлен → возврат → риск», фильтры (площадка, схема, склад, дата); заказ появляется ≤ 15 минут; карточка — сущность (позиции, суммы, статус выплат, связь с клиентом); PII FBS — только ролям Владелец/Логист.
- FR-17: SLA-таймеры отгрузки: таймер на каждом заказе с дедлайном; приближение лимита подсвечивается (пороги настраиваемые); просрочка автоматически создаёт инцидент; ни один дедлайн не «молчит»; пер-площадочная семантика: WB FBS/realFBS — исполнение из Пульта (FR-12), WB FBO — чтение таймлайнов, Ozon — таймеры работают, исполнение Ozon FBS в кабинете площадки (помечается в канбане).
- FR-18: Перемещение заказов по колонкам (вручную и правилами роботов): WB — двусторонняя синхронизация с площадкой; Ozon в Ф0 — статус читается односторонне, ручное перемещение — локальная пометка «у нас» (не пишется в Ozon) с честной подписью в UI; ручное перемещение журналируется; роботы действуют только через action-bus с политиками.
- FR-19: Остатки по SKU с аналитикой: доступный остаток по складам и схемам, дни продаж, покрытие прогноза, флаг «протухающих» (платное хранение); синхронность со сверками FR-9; порог алерта «SKU X на N дней» — настраивается и создаёт задачу (FR-28).
- FR-20: Маппинг с обучением: вероятностное сопоставление SKU ↔ позиций портала обучается на подтверждениях; подтверждённые пары — «знание» портала (осадок данных); каждое подтверждение повышает долю автопокрытия (метрика видна); авто-повтор матчинга по расписанию.
- FR-21: Очередь разборов и bulk-маппинг: кандидаты после блокинга (≤ единиц на SKU); привязка ≤ 2 клика; импорт CSV/Excel «артикул площадки → артикул/штрихкод портала» с валидацией и отчётом об ошибках до применения; групповые привязки пачками с журналом и отменой пачки; 10К+ SKU — 15–25 чел.-часов.
- FR-22: Полная стоимость каждого SKU: комиссия категории, логистика (включая возвраты), платное хранение по дням, эквайринг, штрафы, доля рекламы, налоговый режим; лестница «выручка → … → чистый остаток» за произвольный период (UJ-3: 4 клика); составные части соответствуют тарифам площадок 2026 (конфиг, протокол мониторинга); каждая статья — в ₽ и в %.
- FR-23: Чистая маржа по заказу/SKU/категории/каналу с трендами; «до налога»/«после налога» раздельно (связка FR-27); тренды период-к-периоду; доступ по ролям (финансист/владелец — полный).
- FR-24: Календарь выплат WB и Ozon: «деньги на руках» vs «в пути», план/факт по каждой площадке, детализация удержаний по заказу; факт vs план отклонения за порог → инцидент (FR-25).
- FR-25: Фоновая сверка денег: конвейер сверяет расчётные и фактические выплаты/удержания (цикл не реже ежедневного); расхождение → инцидент с суммой ущерба (видна в очереди инцидентов и журнале).
- FR-26: Себестоимость единицы: ввод входной цены закупки вручную или пачкой по CSV; маржа после закупки; без себестоимости маржа помечается «без учёта закупки»; единый UX импорта с FR-21.
- FR-27: Налоговый радар: текущий режим (УСН/ОСНО), близость к порогу УСН-НДС (20 → 15 → 10 млн ₽ по годам), эффект НДС 22% в цепочке, маржа до/после налога; прогнозная дата достижения порога по текущему темпу; пороги — конфигурационный контур (не хардкод); дисклеймер «не бухгалтерская отчётность».
- FR-28: Задачи из событий (движок правил): событие конвейера/порога автоматически создаёт задачу с владельцем (по роли), приоритетом и дедлайном; типовые правила Ф0: «заказ в риске», «SKU на N дней», «расхождение остатков», «расхождение выплаты»; 100% триггеров → задача ≤ 5 минут; задача содержит ссылку на сущность и сумму ущерба; правила кастомизируются без кода в пределах лайт-набора.
- FR-29: Роли команды и PII-границы: 5 ролей × 6 зон видимости (матрица эталона); PII покупателей — только Владелец и Логист (маскирование для остальных, попытка доступа журналируется); токены видит и меняет только Владелец; тариф «Старт» — 2 роли; назначение в онбординге и настройка позже.
- FR-30: Журнал инцидентов «что случилось — кто спас — сколько сэкономлено»: по каждому инциденту время обнаружения, владелец, время закрытия, оценка ущерба; «спасённые деньги» суммарно за период; оценка — по фиксированной методике классов событий (расхождение сумм — абсолютное значение; предотвращённая потеря заказа — маржа заказа; риск просрочки SLA — тариф площадки); методика опубликована, суммы помечены «оценка»; журнал питает брифинг и North Star SM-3.
- FR-31: Детектор аномалий (правила + статистика, без LLM): скачки/падения заказов по SKU, расхождения остатков, нехарактерные комиссии/удержания, «протухающие», приближение порогов налога; каждая аномалия — с объяснением «что отклонилось и на сколько»; пороги настраиваются; доля ложных срабатываний отслеживается (SM-C1); деньгосодержащая аномалия → задача (FR-28).
- FR-32: Утренний брифинг к 8:00 местного времени портала: здоровье (индекс), ключевые цифры вчера, очередь «что сделать сегодня», инциденты ночи, аномалии, дайджест правил; собирается из витрин со штампом «данные на момент»; доставка внутри приложения/канала уведомлений Б24.
- FR-33: Дайджест изменений правил (M11-лайт): тарифы площадок, пороги УСН-НДС, контрольные точки 289-ФЗ, новые группы «Честного знака» — по периметру портала; редактируемый контур (не хардкод); персонализация по группам товаров портала (после маппинга FR-20).
- FR-34: Пер-тенант квоты и тарифная сетка Старт/Оператор/Сеть: заказы ≤ 2 000/10 000/30 000 на кабинет, SKU ≤ 1 000/3 000/10 000, кабинеты 1/1–3/5, роли «Старт» — 2; превышения — мягкая блокировка (предупреждение → ограничение) с объяснением и предложением пакета; сетка публикуется целиком, недоступное помечается «в разработке»; пакеты применяются без миграции данных; тяжёлый клиент не влияет на SLA лёгких (A-5).
- FR-35: Тарифная заглушка «+ИИ-роль» (каркас): слоты ИИ-ролей (идентификаторы, цены-заглушки 990–2 990 ₽) в биллинг-модели и витрине тарифов с Ф0 («скоро», покупка невозможна); WTP-тест может изменить цифры, но не структуру сетки.

### NonFunctional Requirements

- NFR-1 (доступность): SLA приложения 99,5%/мес; RTO 4 ч; RPO 15 мин (PRD §10, AD-17).
- NFR-2 (безопасность): токены площадок AES-256; PII-минимизация, маскирование по ролям, журнал доступа к PII; РФ-хостинг с геораспределением; IR-план с уведомлением РКН ≤ 24 ч (AD-16).
- NFR-3 (производительность): каталоги до 10К+ SKU на портал без деградации других порталов (стресс-закладка 100К, A-5); события — минуты (новый заказ ≤ 15 мин), витрины/аналитика ≤ 1 ч (AD-29: p99 чтения канбана < 100 мс, k6-профиль «1000 пользователей» перед продом).
- NFR-4 (изоляция тенантов): физическое партиционирование витрин и очередей по organization_id (A-3/AD-4); демо-порталы изолированы (AD-27).
- NFR-5 (наблюдаемость): журнал целостности — пользовательский артефакт; метрики стадий конвейера (лаги, ошибки, сверки) в Prometheus; сквозной request_id; синтетические пробы 15 мин; алерты порогов эталона; статус-страница (AD-18).
- NFR-6 (идентификация): вход и роли — только через контур Б24; никаких отдельных паролей в Ф0.
- NFR-7 (комплаенс): 152-ФЗ/420-ФЗ (локализация ПДн РФ), налоговый контур 2026 — конфигурационный контур (не хардкод), 289-ФЗ — дайджест, «Честный знак» — алерты групп, правила Маркета Б24, СНГ — красная линия Ф0; бюджет инференса Ф0 не применим (ноль LLM, AD-21).

### Additional Requirements

- AR-1 (стек, AD-20/AD-28/Stack): бэкенд — Rust stable 1.99.x (Tokio 1.54, Axum 0.8, SQLx 0.9); PG 18 = system of record (миграции `sqlx migrate`, forward-only); ClickHouse 26.8 — только производные витрины; RabbitMQ 4.4 quorum — журнал событий конвейера; Valkey 9.1 — кэш/локи/rate-limit/pub-sub, **НЕ Redis™** (AD-28: CI-grep запрещает docker-образ `redis:`); фронтенд React 19 + Vite 8, TypeScript.
- AR-2 (гексагональность, AD-1): домены `core/*` не импортируют `adapters`/`shells`; порты — `core/*/ports.rs` (Rust-trait); lint-правило в CI; ноль бизнес-логики в оболочках.
- AR-3 (Structural Seed, spine): каталог `pult/` (gateway, core/{sync,data,finance,shturman,rules,billing,identity}, conveyor/{adapters,action_bus,reconciliation,workers}, shells/bitrix24, platform, db, deploy) — создаётся Epic 1 Story 1 (стартовый каркас).
- AR-4 (конвенции): деньги — integer-копейки (никогда float); ID — UUIDv7; время — timestamptz UTC, в API ISO-8601 с зоной; ошибки — конверт `{error: {code, message, request_id, details}}`; события — past-tense; витрины несут штамп «данные на момент» {organization_id, источник, fetched_at, built_at, reconciliation_cycle_id} (AD-14).
- AR-5 (идемпотентность, AD-15): все внешние write-пути и приём вебхуков — с идемпотентными ключами; доставка at-least-once + дедуп в core/sync; ключи поллинга — hash(площадка, тип сущности, внешний id, revision), вебхуков — внешний event id.
- AR-6 (token-vault и PII, AD-16): токены — AES-256-GCM в KMS-конверте, доступ только интеграционному слою; PII-манифест — единственный источник правды о PII-колонках; CI-тест запрещает PII-колонки в схемах ClickHouse-витрин; каждое обращение к PII журналируется.
- AR-7 (событийный конверт, AD-22): события — JSON `{event_id: UUIDv7, event_type: past-tense, organization_id, occurred_at, schema_version, payload}`; канонические контракты версионируются в ports.rs + schema-registry; консьюмеры толерантны к неизвестным полям; нормализация статусов площадок — домен core/sync; все HTTP-вызовы площадок — только через единый rate-limit-менеджер platform/ (Valkey-счётчики; истина для биллинга — PG).
- AR-8 (домены, AD-23/24/25): «задача» и «инцидент» — единая модель рабочих элементов домена core/rules (один enum приоритетов, дедупликация «один триггер → один элемент»); бизнес-время — IANA-таймзона портала (локальный день — витрины «вчера»/брифинг; таймеры — UTC); расчёт маржи — только core/finance, округление ROUND_HALF_UP до копеек; ClickHouse не вычисляет маржу заново.
- AR-9 (масштабируемость, AD-29): gateway/workers — stateless за LB без sticky-sessions; PgBouncer (пул к primary ≤ ~100); чтение аналитики с реплики; WS-фанaут через Valkey pub/sub; autoscale воркеров по глубине очередей; backpressure — управляемая деградация («медленнее, но достоверно», никогда «тихая потеря»); статика — CDN.

**And** противоречие локальной пометки и прочитанного статуса площадки разрешается честно: пометка «у нас» отображается рядом с площадочным статусом, не вместо него.

## Epic 5: Остатки и номенклатура — ничего не «разъехалось»

Видимость остатков по SKU и разбор несопоставленной номенклатуры: закрывает потери «товар кончился» и «остатки разъехались» (UJ-1).

### Story 5.1: Витрина остатков по SKU с аналитикой

As a селлер,
I want видеть остатки по каждому SKU со днями продаж и флагом «протухающих»,
So что я заказываю закупку вовремя и не плачу за хранение мёртвого товара (FR-19, AD-14).

**Acceptance Criteria:**

**Given** синк остатков обеих площадок жив (сверки FR-9 — их часть),
**When** селлер открывает витрину остатков,

**And** остатки синхронны со сверками: расхождение = инцидент (FR-9), у витрины — штамп «данные на момент» (AD-14),

### Story 5.2: Маппинг с обучением на подтверждениях

As a селлер,
I want чтобы каждая моя привязка SKU училась дальше — и автопокрытие росло,

**When** селлер подтверждает или отклоняет пару,

**And** отклонение кандидата тоже учится (отрицательные сигналы), матаппинг не предлагает отклонённое повторно без новых данных.

### Story 5.3: Очередь разборов и bulk-маппинг

As a селлер с большим каталогом,
I want разбирать несопоставленные SKU пачками и импортом CSV/Excel,

## Epic 6: «Настоящая маржа» — финансы и юнит-экономика

Главный аха-момент продукта: полная стоимость каждого SKU и честная маржа. Реализует UJ-3 («настоящая маржа за 4 клика и минуту»), UJ-5.

### Story 6.1: Финдвижок полной стоимости SKU

As a селлер,

**Acceptance Criteria:**

**Given** синк заказов, выплат и тарифов обеих площадок жив,

**And** расчёт выполняет ТОЛЬКО core/finance (AD-25): результат — в PG; ClickHouse-витрины хранят/агрегируют, но не вычисляют заново; округление — ROUND_HALF_UP до копеек; деньги — integer-копейки (AR-4),

### Story 6.2: Чистая маржа по заказу/SKU/категории/каналу

**And** маржа «до налога»/«после налога» раздельна (связка с налоговым радаром Story 6.6),
**And** доступ по ролям: Финансист и Владелец — полный; остальные — по политике портала (FR-29; матрица — Story 7.2),
**And** без себестоимости маржа помечается «без учёта закупки» (не путается с чистой — Story 6.5).

### Story 6.3: Календарь выплат WB и Ozon

## Epic 7: Команда и процессы — задачи из событий, роли, журнал инцидентов

События конвейера автоматически становятся задачами; роли ограничивают видимость с PII-границами; правила-роботы канбана работают через action-bus безопасно; журнал инцидентов копит доказательства ценности.

### Story 7.1: Движок правил — задачи из событий

As a селлер,
I want чтобы события конвейера и порогов автоматически становились задачами с владельцами и дедлайнами,
So что команда делает работу, а не мониторит кабинеты (FR-28, AD-23).

**Acceptance Criteria:**

**Given** событие конвейера или порога (в т.ч. `stock.threshold.reached` из Story 5.1, аномалии Epic 8),
**When** движок правил (core/rules) применяет типовые правила Ф0 («заказ в риске — N часов до лимита», «SKU X осталось на N дней — решить закупку», «расхождение остатков по складу — проверить», «расхождение выплаты — разбор»),
**Then** задача создаётся ≤ 5 минут с момента события: владелец по роли, приоритет, дедлайн, ссылка на сущность и сумма ущерба (если измерима),
**And** «задача» и «инцидент» — единая модель рабочих элементов core/rules (AD-23): один enum приоритетов, дедупликация «один триггер → один рабочий элемент», нативные задачи Б24 — только экспорт-зеркало, не источник истины,
**And** правила кастомизируются без кода в пределах лайт-набора Ф0: пороги и владельцы по ролям — конфигурация,
**And** очередь «что сделать сегодня» (Story 3.3) и журнал (Story 7.4) — проекции этой модели.

### Story 7.2: Матрица ролей и PII-границы (enforcement)

As a владелец портала,
I want чтобы каждый сотрудник видел только свою зону, а PII покупателей — только мы с логистом,
So что доверие команды и 152-ФЗ не нарушаются (FR-29, AD-16, AD-13).

**Acceptance Criteria:**

**Given** роли назначены (Story 1.6) и запрос идёт через gateway,
**When** пользователь обращается к данным,
**Then** матрица 5×6 enforced на шлюзе: Владелец — всё; Операционный менеджер — заказы полный, финмодель просмотр, цены в лимитах, настройки/токены — нет; Логист — отгрузки/поставки полный, свои склады, без финансов; Финансист — финмодель полный, заказы/поставки просмотр; Контент-менеджер — в Ф0 просмотр заказов без PII (зона отзывов — Ф2),
**And** PII-маскирование на шлюзе для всех, кроме Владелец/Логист; каждая попытка доступа к PII журналируется (кто/что/когда); PII-манифест — единственный источник правды о PII-колонках, CI-запрет PII в ClickHouse-витринах (AD-16),
**And** токены площадок видит и меняет только Владелец; квота ролей тарифа enforced («Старт» — 2; расширение — пакет, Story 9.1),
**And** вход и роли — только через контур Б24 (NFR-6); матрица тестируется контрактными тестами шлюза (позитивные/негативные по всем 5 ролям).

### Story 7.3: Правила-роботы перемещения заказов (через action-bus)

As a селлер,
I want чтобы рутинные перемещения заказов по канбану делались роботами по правилам,
So что рука не тянется к каждой карточке, а автоматизация — безопасна (FR-18-роботы, AD-7, A-8, A-9).

**Acceptance Criteria:**

**Given** правила-роботы настроены (условие → действие: перемещение колонки),
**When** условие срабатывает,
**Then** робот действует ТОЛЬКО через action-bus с политиками (AD-7: кто/что/в каких лимитах/с каким журналом), идемпотентно, с журналом (кто/когда/результат); для WB — двусторонняя синхронизация, для Ozon — локальная пометка (честная подпись, как Story 4.3),

**And** события правил пишутся в data-flywheel журнал (A-7: контекст → действие → исход) — база будущих ИИ-ролей с первого пилота,
**And** правовой контур (A-11): дисклеймер «операционная работа, не консультация»; лимиты ответственности — каркас оферты.

### Story 7.4: Журнал инцидентов «что случилось — кто спас — сколько сэкономлено»

As a селлер,
I want журнал всех инцидентов с оценкой предотвращённого ущерба,
So что ценность продукта измерима в рублях (FR-30, A-7, SM-3).

**Acceptance Criteria:**

**When** селлер открывает журнал инцидентов,
**Then** по каждому: время обнаружения, владелец, время закрытия, оценка ущерба/предотвращённого ущерба; «спасённые деньги» показаны суммарно за период (₽),
**And** оценка — по фиксированной методике классов событий: расхождение сумм (комиссия/логистика/выплата) — абсолютное значение расхождения; предотвращённая потеря заказа — маржа заказа; риск просрочки SLA — стоимость по тарифам площадки; методика опубликована в приложении, суммы помечены «оценка» (SM-C1 — подтверждение сверкой или фактом площадки),

So что налоговый и маркировочный контур 2026 не застаёт врасплох (FR-33).

**Acceptance Criteria:**

**Given** редактируемый контур волатильных факторов (конфиг-таблицы: тарифы площадок, пороги УСН-НДС, контрольные точки 289-ФЗ, группы «Честного знака»),
**When** меняется правило/тариф/порог из периметра портала,
**Then** в брифинг попадает персонализированный дайджест: только группы товаров и правила, релевантные SKU портала (после маппинга FR-20),
**And** контур редактируемый (обновление без релиза кода; протокол мониторинга гл. 5 эталона; использование волатильного факта старше цикла мониторинга без проверки — ошибка проектирования),
**And** правило эталона честности: дайджест не заменяет консультацию (дисклеймер),
**And** в Ф0 дайджест — только информирование; очередь контрольных точек M11 (комплаенс-радар) — Ф1–Ф2.

## Epic 9: Тарифы и квоты — прозрачная витрина

Сетка Старт/Оператор/Сеть с per-tenant квотами (пул подписки Б24), мягкой блокировкой и честной витриной с заглушками «+ИИ-роль».

### Story 9.1: Пер-тенант квоты и тарифная сетка (enforcement)

As a селлер,
I want понятные квоты моего тарифа и мягкое превышение с предложением пакета,
So что счёт предсказуем, а рост — без миграций (FR-34, AD-5, AD-6, AD-24).

**Acceptance Criteria:**

**Given** портал тарифицируется по сетке Старт/Оператор/Сеть,
**When** биллинг-контур проверяет квоты (заказы ≤ 2 000/10 000/30 000 на кабинет; SKU ≤ 1 000/3 000/10 000; кабинеты 1/1–3/5; роли «Старт» — 2),
**Then** лимиты enforced на шлюзе и планировщиком воркеров; счётчик-истина — PG (AD-5); месяц — календарный по зоне портала (AD-24); предполётная проверка квоты каталога ДО старта первичного синка,
**And** превышение — мягкая блокировка: предупреждение → ограничение аналитических витрин и автодействий + предложение пакета; приём заказов, инциденты, сверки и SLA-механика квотой НЕ ограничиваются (AD-5: SLA-инвариант главнее квот — «ноль тихих потерь»),
**And** пакеты объёма («+5 000 заказов», «+5 000 SKU», «+1 кабинет») применяются без миграции данных; квоты и счётчики видимы пользователю в настройках,
**And** тяжёлый клиент не влияет на SLA лёгких (fair-scheduling, Story 2.3); сетка публикуется целиком, недоступные позиции помечены «в разработке» (не скрыты).

### Story 9.2: Витрина тарифов с заглушкой «+ИИ-роль»

As a селлер,
I want видеть всю тарифную сетку честно — включая то, что готовится,
So что я планирую рост без сюрпризов смены условий (FR-35, A-10, A-11, AD-11).

**Acceptance Criteria:**

**Given** биллинг-модель ядра,
**When** рендерится витрина тарифов,
**Then** в модели существуют слоты ИИ-ролей (идентификаторы, цены-заглушки 990–2 990 ₽/мес) с Ф0 — каркас (A-10), покупка в Ф0 невозможна (кнопка «скоро», не «купить»),
**And** витрина честно помечает недоступное («в разработке»), не продавая обещания; WTP-тест Ф2–Ф3 может изменить цифры, но не структуру сетки (A-10/AD-11),
**And** структура биллинг-модели стабильна: активация ИИ-ролей в Ф2 не перекраивает сетку (инвариант AD-11); слоты ролей связаны с сеткой автономии (A-8) и правовым контуром (A-11: лимиты ответственности — каркас оферты),
**And** текущее списание — пул подписки Б24 (SLA-компенсация — «месяц без начисления усилий», Story 2.6).
