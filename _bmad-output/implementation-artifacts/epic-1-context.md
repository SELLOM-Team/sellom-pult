# Epic 1 Context: Подключение селлера — от установки Б24 до первого живого канбана

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Эпик активации: селлер устанавливает приложение «Пульт селлера» из Маркета Битрикс24 и за ≤ 15 минут активного времени честно проходит фильтр периметра, подключает Wildberries и Ozon (чтение обеих схем), получает первичный синк истории с видимым прогрессом, маппинг номенклатуры, пороги и роли — и видит первый живой канбан. Демо-кабинет и виджет Б24 показывают ценность без передачи токенов. Гейт фазы: канбан жив ≤ 24 ч у 80% пилотов. Story 1.1 создаёт Structural Seed — стартовый каркас всей системы, без него не начинается ни одна последующая сторис.

## Stories

- Story 1.1: Стартовый каркас приложения и Structural Seed
- Story 1.2: Шаг 0 — фильтр периметра «ваш бизнес»
- Story 1.3: Мастер подключения площадок с token-vault (шаги 1–3)
- Story 1.4: Первичный синк истории и первый канбан
- Story 1.5: Маппинг номенклатуры при онбординге (шаг 4)
- Story 1.6: Пороги алертов и роли команды (шаги 5–6)
- Story 1.7: Демо-кабинет №1
- Story 1.8: Виджет Б24 «остатки и статус дня»

## Requirements & Constraints

- **Шаг 0 (FR-1):** минимальный вопросник модели торговли без PII; не-селлер получает честный отказ «продукт не подходит» и рекомендацию партнёра (рев-шер ≥ 30%) и не попадает в воронку; шаг запоминается per-user и не повторяется; доля прошедших замеряется (знаменатель активации).
- **Подключение площадок (FR-2):** WB — полная глубина FBO/FBS/realFBS; Ozon — только чтение обеих схем FBO+FBS/rFBS (заказы, остатки, тарифы, выплаты; без обратной записи). Токен принимается только после автотеста прав: успех — список подтверждённых прав, отказ — человекочитаемая диагностика без стек-трейсов. Права перепроверяются при каждом цикле синка; провал — пауза сбора со статусом «требует внимания», не полурабочее состояние. Обе площадки подключаются одновременно в одном портале; несвязанные кабинеты — раздельно. Токены видит и меняет только роль Владелец.
- **Первичный синк (FR-3):** активная часть онбординга ≤ 15 минут, полный синк ≤ 24 часов; прогресс виден (что синхронизируется, %, оценка завершения). Тяжёлый каталог 10К+ SKU не блокирует лёгкие порталы. «Первый канбан» — 7 колонок без фильтров (полный канбан — Epic 4). В UI честно: «Ozon подключён, данные после завершения адаптера».
- **Маппинг (FR-4):** доля автопокрытия — живая метрика онбординга; подтверждение привязки ≤ 2 кликов; непокрытые SKU — очередь разборов; каждая подтверждённая пара обучает матчинг и журналируется (кто/когда).
- **Пороги и роли (FR-5):** пороги (дни продаж, тайминги отгрузки) — редактируемая конфигурация портала, не код; приглашения — только внутри контура Б24; справочник 5 ролей (Владелец, Операционный менеджер, Логист, Финансист, Контент-менеджер); онбординг завершается канбаном с ≥ 1 назначенной ролью и заданными порогами; тарифная квота отображается честно («Старт — 2 роли»). Маскирование PII по ролям включается сразу для подключённых данных (границы Владелец/Логист для FBS-контактов).
- **Демо-кабинет (FR-6):** открывается со страницы приложения в Маркете без регистрации; синтетика — 3 SKU, 2 площадки, инциденты, неделя истории, сезонность, тарифы 2026; все экраны помечены «демо-данные».
- **Виджет Б24 (FR-7):** остатки и статус дня с лагом ≤ аналитического цикла (минуты–час) и штампом «данные на момент»; клик открывает приложение на нужном разделе (deep-link).
- **Авторизация (NFR-6):** вход и роли — только через контур Б24; никаких отдельных паролей.

## Technical Decisions

- **Hexagonal (AD-1/AD-22):** домены `core/*` не импортируют `conveyor/adapters` и `shells` (lint в CI); ноль бизнес-логики в оболочках; порты — пустые lib-заготовки `core/*/ports.rs` (Rust-trait), версии контрактов и событийный конверт `{event_id: UUIDv7, event_type: past-tense, organization_id, occurred_at, schema_version, payload}`.
- **Стек (AD-20):** Rust stable 1.99.1 (фиксируется `rust-toolchain.toml`), Tokio 1.54.1, Axum 0.8.9 (REST-шлюз), SQLx 0.9.0 (compile-time SQL, миграции); SPA — React 19 + Vite 8 + TypeScript в shells/bitrix24.
- **Инфраструктура:** docker-compose поднимает PG 18 + RabbitMQ 4.4 (quorum-очереди) + Valkey 9.1 (образ `valkey/valkey`). Valkey, НЕ Redis™: docker-образ `redis:` — ошибка CI-грепа (AD-28); все эфемерные состояния (кэш, локи, rate-limit, pub/sub) — только Valkey.
- **Structural Seed:** воркспейс `pult/` — gateway/, core/{sync,data,finance,shturman,rules,billing,identity}, conveyor/{adapters,action_bus,reconciliation,workers}, shells/bitrix24/, platform/, db/, deploy/; первые миграции `sqlx migrate` (forward-only) — только organizations, users, role_assignments, portal_settings; таблицы создаются сторис под собственные нужды.
- **CI-гейты:** build + clippy/test + hexagonal-lint + Valkey-греп + bundle-size: критический путь SPA < 200 КБ gzip (AD-30).
- **Token-vault (AD-16):** токены площадок шифруются AES-256-GCM в KMS-конверте; расшифровка только в интеграционном слое; plaintext в БД ловит CI-тест; ротация без расшифровки в логах.
- **Идемпотентный событийный конвейер:** доставка at-least-once + дедуп, ключ приёма `hash(площадка, тип сущности, внешний id, revision)` (AD-15); чекпоинты по `(organization_id, тип цикла)` — повтор после сбоя продолжает с чекпоинта (AD-3). Минимальный вертикальный срез Story 1.4: adapter → RabbitMQ (приоритеты, партиции по organization_id) → worker → PG.
- **Fair-scheduling (AD-6):** гарантированная доля слотов воркеров на организацию — тяжёлый портал не вытесняет лёгкие.
- **Матчинг (A-1):** блокинг-предфильтр (категория, бренд, нормализованный артикул) до вероятностного сравнения — контракт конвейера, не оптимизация; вероятностный матчинг только предлагает кандидатов, привязку подтверждает человек (автономия ≤ L1).
- **Демо-изоляция (AD-27):** флаг `demo`, отдельные партиции, синтетика без реальных PII, наинизший приоритет в очередях, пул Б24 не начисляется; CI-тест изоляции.
- **Конвенции:** деньги — integer-копейки (не float); ID — UUIDv7; время — timestamptz UTC; ошибки — конверт `{error: {code, message, request_id, details}}`.

## UX & Interaction Patterns

UX-контракт ещё не создан — вопрос формата виджета Б24 (типовой/REST/инлайн) открыт до UI M1, каркас должен поддерживать оба варианта. До его появления UI-сторис опираются на: честные подписи (включая статус Ozon-данных), осмысленные пустые состояния, скелетоны вместо спиннеров, штампы «данные на момент» и бюджеты производительности (AD-30): LCP < 2 с, INP < 200 мс, CLS < 0.1 — CI-гейт; виджет < 150 КБ gzip и не блокирует интерфейс Б24.

## Cross-Story Dependencies

- Story 1.1 (Structural Seed) — фундамент всех сторис эпика и последующих эпиков.
- Цепочка онбординга: 1.2 (в воронку входят только прошедшие фильтр) → 1.3 → 1.4 (синк стартует только с подтверждёнными токенами WB) → 1.5 (матчинг — после завершения синка каталога) → 1.6 (шаг 7 — контрольная точка завершения онбординга).
- 1.7 и 1.8 не зависят от онбординга, но требуют каркаса 1.1; 1.8 показывает данные только при живом синке (1.4).
- Ozon-заказы появятся в канбане только после адаптера Ozon (Epic 2, Story 2.2) — в этом эпике подключаются токены и схемы.
